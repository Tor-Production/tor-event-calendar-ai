# Connections

## Remote plugin connection

The ordinary route is one calendar plugin installation, then browser sign-in, account choice, and consent when the host requests it. The plugin supplies the remote MCP connection and skill together; no user-provided MCP URL, Node installation, local helper, or API token is required. The MCP resource is `https://nambli.com/mcp`; OAuth issuer is `https://nambli.com/api/v1/auth`. Ask for `calendar.read` to read and `calendar.manage` for writes or File upload links; `offline_access` permits refresh across access-token expiry. Consent is specific to the selected calendar account and exact server origin. Choose the intended connected account in the host and verify it with `get_profile`; a website login change does not move an existing grant. To disconnect/revoke when the user asks, use the host's plugin connection settings or the calendar's account connection controls; never ask the user to share a token.

## Host account management

Open nambli's installed plugin card in the host and use its **Apps** connection entry to reach **Connected accounts**. Where supported, this page shows the current **Primary** account and **Connect another account**. Use the account controls exposed by the current host and installed plugin; do not invent a deep link or reuse another user's private account-management URL. If the host does not expose these controls, explain that limitation and direct the user to its supported connection settings.

Add another account only when requested; preserve the existing accounts. A direct MCP server's gear opens server configuration, and its standalone grant is separate from the App's connections. Prefer exposed App-backed tools when using the host's account selection. Call `get_profile` through the selected route and use its verified identity for that operation; do not fall back to a different grant or a remembered email. When no matching tool is exposed, state that limitation and offer the account manager rather than claiming a profile lookup succeeded.

## Moving an existing connection to nambli

nambli's current MCP resource is `https://nambli.com/mcp` and its OAuth issuer is `https://nambli.com/api/v1/auth`. A grant for `https://eventcalendar.torproduction.com` or the former workers.dev origin stays bound to that origin and does not move by redirect or a display-name change. Existing clients continue to use their saved origin until you deliberately reconnect.

For an AI client, update or reinstall its connection configuration for the nambli MCP URL, start a fresh browser sign-in, choose the same verified calendar account, and review the new grant. Confirm `get_profile` and a bounded read before revoking the older connection in its account settings. Do not copy access or refresh tokens between origins. Signing in to the website alone does not connect the AI client.

The 0.2.0 CLI defaults new connections to nambli. Its technical command, profile directory, keyring service and origin-bound profile IDs remain unchanged so existing connections remain accessible. After installing version 0.2.0 or later, run `tor-calendar connect --origin https://nambli.com --default`, then `tor-calendar accounts list` and `tor-calendar whoami` to verify the new default. The old profile remains present; use its exact profile ID when deliberately disconnecting it. If the same email exists on both origins without a default, select an exact profile ID. The published v0.1.0 CLI still defaults to workers.dev; it can explicitly connect to nambli with `--origin https://nambli.com`. Upgrading never rewrites a saved profile origin or transfers a credential.

## Optional local CLI

Use this route only when the user explicitly chooses the local CLI. If `tor-calendar` is unavailable, check that this host supplies a local Node 22.18+ shell and an unlocked OS keychain. Use the exact 0.3.2 GitHub release tarball and its recorded SHA-256, or an explicitly selected local checkout (`node src/cli.mjs version`). The GitHub package release is separate from the OpenAI store listing; it does not establish catalog approval or a native-client acceptance result. Existing release artifacts retain their original bytes. Check `version`, then run `connect` for browser approval. This is a separate connection from the remote plugin. If this host cannot execute a local CLI/use its secure store, report that concrete limitation; do not claim a connected account or read someone else's secrets.

The CLI runs locally with Node 22.18+ and stores tokens in Windows Credential Manager, macOS Keychain or Linux Secret Service via pinned `@napi-rs/keyring` 2.1.0. Linux explicitly requires Secret Service; a missing/locked store fails closed. Only non-secret profile metadata is written to `%LOCALAPPDATA%/tor-event-calendar/profiles.json` (Windows) or `~/.config/tor-event-calendar/profiles.json` (macOS/Linux), outside repositories and installed skills.

`connect [--scope read|manage] [--name DEVICE] [--no-browser] [--default]` starts a device authorization pattern with a 10-minute single-use code, 5-second minimum polling and an S256 verifier binding. Check the browser's verified email, immutable calendar account ID, requesting device, code and requested permission. The token appears only in the HTTPS exchange and OS keychain; it is never printed or placed in argv, URLs, prompts or browser storage. Consent connects this local runtime only. `read` cannot mutate; `manage` covers calendar CRUD, files, preferences, receipt reporting and publication claims, not social network authorization. Paired tokens expire after 90 days and can be revoked independently.

`accounts list`, `accounts default VERIFIED_EMAIL_OR_ID`, `whoami --account SELECTOR`, `status`, and `disconnect --account SELECTOR` manage multiple connections. A single profile can be used without another approval. Multiple profiles need an explicit selector or explicitly selected default; every batch pins an immutable origin/account. Email is server-verified human metadata, not ownership. Changes to email refresh the same ID's metadata. Invalid/revoked credentials and mismatches never fall through to another profile or cookie. Reconnect only updates that profile; previous tokens remain visible for revocation in browser settings. Existing unrelated helper/automation tokens are preserved.

`disconnect` revokes this connection then removes the local credential/profile. `--local-only` forgets it locally, for example after independent browser revocation; it does not claim server revocation. Upgrading or uninstalling the CLI/skill leaves profiles and keychain intact. The skill installer replaces only its marked installations; it refuses an existing junction or unowned skill. Preserve an owner's junction and update its source deliberately.

All local agent ecosystems under the same OS user can reuse one CLI connection. Each other machine/cloud/container needs its own connection or secret-manager injection. ChatGPT cloud cannot access the local keychain. The local CLI uses its own browser pairing and token; the remote MCP OAuth connection is separate.

Headless route: use your runtime's secret manager to inject `TOR_EVENT_CALENDAR_API_TOKEN`, then explicitly pass `--environment --account IMMUTABLE_SERVER_ACCOUNT_ID [--origin HTTPS_ORIGIN]`. The CLI verifies `/api/me` before private work. Never type the secret as a command, commit it, or copy it into the chat. This is an explicit environment route, not an automatic fallback. There is no plaintext-file fallback, so Unix chmod is never treated as Windows ACL protection. An owner managing secret files independently must restrict real Windows ACLs or POSIX owner permissions before injection; that file workflow is outside this client.

`doctor` probes a random synthetic keychain entry, deletes it, retrieves public capability limits and lists non-secret profile identity metadata. It makes no private calendar writes or social calls. `whoami` confirms the selected account read-only. Pairing response loss after consumption requires fresh consent; no debug token retrieval exists.
