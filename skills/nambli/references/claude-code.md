# Claude Code workflow

Use this host guidance with the shared calendar skill. Invoke the installed plugin skill explicitly with `/nambli:nambli`; a standalone skill is `/nambli`. Installing or invoking either skill does not authenticate an account. No skill grants blanket tool approval.

## Connection and discovery

Use the selected `nambli` HTTP MCP connection at `https://nambli.com/mcp`. With the plugin, tools have the prefix `mcp__plugin_nambli_nambli__`; a manually added server uses `mcp__nambli__`. Discover the actual exposed tools and input schemas before calling them; tool availability also depends on consent and host policy. `get_capabilities` describes server capabilities, not Claude Code file transport.

For a migration from the former `tor-event-calendar-ai` Claude plugin, verify the current server is `plugin:nambli:nambli` and the new tool prefix before reporting success. Preserve pending disposable event UUIDs, revisions and file evidence for continuation or cleanup. Inspect an old installed entry and its exact scope before disabling it; do not clear credentials, revoke grants or change unrelated installations. Only reauthenticate if the host requests it, then verify the intended account. Existing tool permissions may refer to the old prefix; review the affected rules individually without broadening access. Do not assume OAuth state transfers to the renamed plugin.

If disconnected, explain that no calendar action was performed and direct the user to `https://nambli.com/connect-ai` or the [Claude Code setup guide](https://github.com/Tor-Production/tor-event-calendar-ai/blob/develop/ecosystems/claude-code/README.md). Complete browser OAuth through `/mcp` in an interactive Claude Code session. Never ask for a token, copy a callback URL into a chat, or silently switch to the local helper.

Call `get_profile` and confirm its stable `id` and verified `email` against the intended calendar account before private reads or writes. Pin that connection. Use `list_events` with a bounded range or `localDate` and IANA `timeZone`, then `get_event` for exact IDs only. On missing scope, reauthorize in `/mcp`; on expiry, use the host refresh or re-authentication flow and verify identity again. Website account switching does not transfer a grant.

Use `prepare_event` and its same stable UUID for `create_event`. After an uncertain result, read that UUID before retrying. Read the current `revision` before `update_event` and provide it as `eventRevision`; after a stale revision, reread and resolve the conflict. Read back saved text, time, timezone, typed fields and settings. Calendar writes never publish or schedule social posts. They can make reminders eligible under notification preferences the user enabled separately; MCP cannot opt an account into notifications. For connector checks, use the historical fixture and have the tester pause their own notifications before creating disposable records.

## Upload files

Claude Code local files are not the remote `upload_file.file` contract. That argument requires host-provided temporary metadata (`download_url`, `file_id`, optional MIME/name) from an accepted OpenAI/Azure source. Claude Code has no demonstrated bridge for that contract. A visible `upload_file` tool or a server capability flag does not prove native file input. Do not send a local path, invent temporary URLs or file IDs, base64-encode bytes, or extract credentials. For user-selected automatic local uploads, use the bundled helper route below. For other requests, retain the authenticated browser fallback unless the actual host file transport is separately verified.

1. Identify the exact owned event and requested target field. Read its latest revision. If needed, use `update_event` to declare `customFieldTypes: {"image": "File"}` (substitute the user's field name), with no value for that File field in `customFieldUpdates` or `customFields`. Preserve all other fields.
2. Call `get_file_upload_link` with the exact `eventId` and `fieldName`. Return its observed `uploadUrl`; explain that this action only opens a browser upload form. The browser verifies the account, event ownership and named File field. If the tool is missing, refresh/reconnect; meanwhile the user can open nambli, select the intended account/event, and use that event's explicit File field in its editor.
3. Let the user choose the file and upload in the authenticated form. Maximum size is 25 MiB per file. The form keeps a stable upload UUID for an unchanged uncertain retry, rereads on conflict, and uses a new UUID for an intentional replacement. Do not overwrite an existing field without the user's intent.
4. After browser confirmation, call `get_event` again. Verify the exact field, stable attachment ID, filename, MIME, size and advanced revision. If a compact result omits attachment data, request full content or read bounded chunks at that revision. This verifies persisted metadata. Download and compare bytes separately before claiming a file round trip.

### Agent-run uploads from app attachments

When the user asks you to upload local/chat files automatically, or has already selected this helper route, run the helper commands yourself. The user attaches the image/PDF in the app; use the actual accessible file path supplied by the host. Inspect that attachment's metadata/location or copy its accessible bytes to a task-local staging file if necessary. Never invent a path from the displayed filename or reconstruct a file from a text/image preview. If the host exposes no readable original bytes, report that attachment-access limitation and offer the browser form. An existing path test alone does not verify the app-attachment workflow.

Resolve the actual absolute plugin root from this loaded skill (not the working directory). Read `ecosystems/claude-code/AUTO-UPLOAD.md` under that root. If this is a standalone skills-only install without the bundled helper, state that limitation and offer the complete plugin or browser route. The helper needs Node 22.18+ and npm. Invoke `node "ABSOLUTE_PLUGIN_ROOT/ecosystems/claude-code/local-files.mjs" setup`, then `doctor` and `accounts`. Setup copies this exact bundled source into a hash-specific user cache, installs pinned keychain dependencies without lifecycle scripts, and never writes to the installed plugin directory. It does not pair an account or upload anything.

Use fresh MCP `get_profile` first. Choose a helper profile matching both its stable account ID and `https://nambli.com`. If absent, run the same entrypoint with `connect`, keep it running, and let the user approve their own browser pairing. This local-helper grant is separate from MCP OAuth and its credential stays in the OS keychain; never extract or copy credentials. Then run `accounts` and `status --account MCP_ACCOUNT_ID --profile PROFILE_ID`. Stop on a mismatched account, read-only scope or unavailable storage; preserve unrelated profiles. Browser approval is the user's one-time interaction, not a requirement to type CLI commands.

For the user's exact event/File-field intent, read the current MCP event revision and run the entrypoint with `upload EVENT_ID FIELD_NAME "ABSOLUTE_ACCESSIBLE_ATTACHMENT_PATH" --account MCP_ACCOUNT_ID --profile PROFILE_ID --revision CURRENT_EVENT_REVISION`. The runner verifies account, origin, manage scope and revision, then uses the existing tor-calendar multipart implementation. After success, read the event through MCP and verify the receipt's attachment metadata. Reuse setup/pairing on later requests, while rechecking fresh MCP identity for a new session. Do not change global tool approvals or promise unattended permission bypasses.

An unchanged retry derives the same upload UUID from event/field/filename/MIME/bytes. After an uncertain result, read the event first and retry only the unchanged requested file with the newly observed revision if needed. On a stale revision, reread and reconcile; do not silently replace a concurrent edit. Keep the 25 MiB limit, explicit File types, replacement intent and browser fallback. A hash receipt proves uploaded bytes, not a download round trip. For that check, use the entrypoint's `download EVENT_ID ATTACHMENT_ID "NEW_DESTINATION" --account MCP_ACCOUNT_ID --profile PROFILE_ID` and compare hashes. See [local helper connections](connections.md#optional-local-cli).

## Download files

Discover `get_file_download` from shared #66. After `get_profile` and `get_event`, pass the exact `eventId`, current `eventRevision`, `attachmentId`, and explicit `fieldName` (null only for a legacy unbound attachment). Its result contains metadata, `browserUrl`, `bytesDelivered: false`, and a `resourceUri`/resource link for files at most 512 KiB. Read scope is sufficient. An advertised link is not delivered bytes.

If Claude Code actually exposes resource reading and delivery, read that exact authenticated `nambli://` resource with `resources/read` through the connected MCP host. Claude's resource references may be available through `@`; use the actual host affordance and record the result. This is not an HTTP URL for a web tool. Confirm observed bytes and host file access before claiming Claude read the image/PDF. Native resource visibility and decoding remain host acceptance checks; never assume a `resource_link` was read automatically.

When resource delivery is unavailable or the file exceeds 512 KiB, return the tool's observed `browserUrl` and let the user sign in to the matching account and choose **Download file**. This browser page checks the exact attachment and revision; the action itself is not a download receipt. If the new tool is not yet deployed/exposed, refresh the tool list and use the authenticated event editor's saved filename download meanwhile. On `STALE_REVISION`, reread the event and request a fresh action. Deleted, foreign-account or revoked access failures do not authorize trying another account.

The independently paired shared helper also provides `tor-calendar download EVENT_ID ATTACHMENT_ID DESTINATION --account PROFILE_ID` when its installed version advertises `download`. Verify the same stable account/origin first. It retrieves authenticated bytes and reports a local save/hash receipt; preserve an existing destination rather than overwriting it implicitly. If an older helper lacks this command, use the browser or a reviewed source build that includes #66. Never claim the old v0.3.0 release has the new command.

Compare SHA-256 hashes with the original synthetic input for a byte round trip. If the user wants Claude to inspect a browser/helper download, supply the resulting local path only after the host can access it. Never fetch an authenticated URL through an unauthenticated web tool or paste cookie/Bearer credentials into a command. Attachment metadata proves the saved reference, not received bytes.
