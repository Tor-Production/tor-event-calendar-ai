# Explicit publication handoff

The remote calendar MCP exposes only `get_publishing_task` for reading a publication handoff. None of its tools submits, schedules, claims, comments, reacts, or marks a social post as published. The local CLI/bridge protocol described below is an optional advanced route and must not be inferred from plugin installation. If no separately authorized publisher is available for the selected calendar account and exact social actor/target/audience, report the handoff and blocker without claiming publication.

Read/show never publishes. Creating content, storing settings, recording readiness and creating calendar schedules never invokes social services. Publication requires explicit current user instruction for selected account/posts AND separately verified social authorization for the exact actor/target/audience. Never expose owner-specific credential stores to another calendar user.

The local CLI provides an implemented batch workflow with truthful capability blocks. LinkedIn personal/public base-post support exists in the owner's separate browser publisher, but the portable client has no shared social connection. The CLI returns `CONNECT_VERIFIED_LINKEDIN_PUBLISHER_FOR_THIS_ACCOUNT`; X/Reddit currently support planning and return `PLATFORM_PUBLISHER_UNSUPPORTED`. No universal working publisher is advertised. An authorized host bridge must implement `authorize` and `submit` and use this workflow, not invoke an unrelated owner's publisher. Existing owner automations are not changed.

`today --posts` resolves the selected account's explicit timezone preference or supplied `--zone`. It translates local midnight to the next local midnight, including 23/25-hour days, and pages summaries. `publish-today --all` requires an explicit all-matching scope. For selected items, refresh identity/ID/revision/status. Skip published/cancelled records; report missing copy/settings/media/alt text, unresolved external media links, unsupported targets and missing authorization. A native platform queue must be reliably cancelled/reconciled before immediate publication; otherwise block it. A future time can be intentionally overridden for this run without erasing the original schedule.

Before any external submit, the Worker atomically inserts one account/event claim at the current revision. The dedupe key includes canonical origin, account and event and spans sessions/content revisions. Claims have no automatic expiry/unlock. Publication inputs and attachments are frozen while state is `claimed`. An uncertain claim response never authorizes a second attempt. Unknown/failed/pending submissions stay guarded across edits/restarts; reconcile observed platform evidence rather than release the claim to repost.

The host must persist a scoped unknown receipt journal BEFORE external submission. After a confirmed receipt, persist the real external ID/HTTPS URL/time and independent followup outcomes, then call the existing `/publication-result` contract. If callback fails, reconcile the saved receipt without reposting. An ambiguous remote response stays `unknown` and blocks retry. A first comment/reaction/Featured failure does not negate a successful base post. The shipped adapter tests use synthetic accounts and fake external responses, assert exact submit counts and never publish real content.

Results are per event: published, skipped/already published, needs_input, blocked, unknown or failed. A mixed batch never reports all success and never rolls back/repeats successful external posts. Stored calendar readiness is technical evidence only, not consent. A claimed future automatic-runner attempt records intentional-now authorization; it preserves scheduledAt/history. Manual/calendar receipts alone cannot prevent duplicate external submissions, so the claim/journal protocol is required for every participating bridge.
